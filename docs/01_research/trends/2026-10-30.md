### 1.2 この製品への影響（extension/ のコードを読んだ上での整理）
- `extension/manifest.json`：`permissions` は `storage` と `unlimitedStorage` のみ。`host_permissions` は無く、content script の `matches` は `https://www.youtube.com/*` だけ。今回確認した範囲では、これらを変える必要のある変更はなかった。
- `extension/background.js`：service worker は2つのメッセージ中継（`action.onClicked` → `tabs.sendMessage`、`runtime.openOptionsPage`）だけで、状態を持たない。service worker 関連の変更の影響は受けにくい構造（コードを読んだ上での判断）。
- `extension/content.js`：`chrome.storage.local`（チャット保存）と `chrome.storage.sync`（設定 `hlxSettings`）を使っている。sync に大きなデータを入れると 8KB/項目の上限に当たるが、設定だけなら問題ない見込み（設定の大きさは未確認）。local は `unlimitedStorage` があるので 10MB の上限は関係しない。
- ポリシー(b)(a) との関係（推測を含む）：この拡張は、利用者が開いた動画のチャットを取得して端末内に保存・解析する。コード（fetcher.js）を読んだ範囲では、通信先は youtube.com だけで外部サーバーへは送っていない。ただし、拡張全体を検査したわけではない（content.js 全体と options は精査していない）。ストアに出している／出す予定の場合は、「チャットを取得して保存する」旨を掲載文のプライバシー項目に明示することを勧める。ストアに公開しているかどうかは本調査では未確認。
- `shared/` や出力の変更は不要。

### 3.2 この製品への影響（コードを読んだ上での整理）
- **fetcher.js の壊れやすい所**（YouTubeが形を変えると壊れる箇所）
  1. `ytInitialData` / `ytInitialPlayerResponse` を HTML から正規表現で取り出す（`hlxExtractVar`）。取れないと「ページ情報を読み取れませんでした」で止まる。
  2. 場所の指定が深い：`contents.twoColumnWatchNextResults.conversationBar.liveChatRenderer.continuations[0].reloadContinuationData.continuation`。
  3. 全件への切替が `subMenuItems[1]` と **添字固定**。順序が変わると「上位のチャット」のまま取り、コメント数が少なく見える（エラーにならず結果が静かに悪くなる）。yt-dlp も同じ添字固定（比較して確認）なので、YouTubeが変えれば両方が影響を受ける。
  4. `INNERTUBE_API_KEY` は無くても動く書き方（無ければ `key` を付けない）。`INNERTUBE_CONTEXT` が取れないときの代替の `clientVersion` は固定値 `2.20261001.00.00`（古くなる可能性。推測）。
  5. 終端判定は「5回連続で新しいコメントが無い」。`liveChatReplayContinuationData` の名前が変わると途中で打ち切られる（YouTubeが変えた場合の推測）。
- **videoid.js**：`/watch?v=ID` と `/live/ID` のみ対応。`youtube.com`（www なし）・`m.youtube.com`・`/embed/`・`/shorts/` などは対象外。manifest の `matches` も `https://www.youtube.com/*` のみなので、www なしや m. では動かない（コードからの事実。それを望ましいかは要件の判断）。
- **SPA遷移**：content.js は `yt-navigate-finish` イベントを拾い、さらに `location.href` の変化も見る二重の作り（content.js の465〜468行付近）。YouTubeがイベント名を変えても URL の変化で拾える構造。
- **検知の手段**：実配信での確認（運用係の定期スモークテスト）が最も確実。YouTube側の変更は告知されない前提で、スモークテストの失敗を最初の合図にするのがよい。

## 6. 論点（部長・課長へ）
- 「/deep-research 推奨」に当たるテーマ：**YouTube の内部API（チャットリプレイ）が壊れたときの検知と代替手段**。公開の公式APIは無く、告知も無いので、複数の検知手段（実機の定期確認、yt-dlp のリリース監視、利用者の声）の設計を深く調べる価値がある。
- 未確認の事項（調べきれなかったこと）：(a) ストアに公開しているか、(b) Chrome 154〜156 の各安定版の拡張機能向けの変更、(c) 2週間リリースの Google 公式の告知、(d) YouTube の `/live/<ID>` やページ構造の変更に関する外部情報、(e) yt-dlp 2026.10.21 の「初期データの取り出し」の中身、(f) tests/e2e の iframe 使用の有無、(g) imageio-ffmpeg 0.7.0 の変更点。
