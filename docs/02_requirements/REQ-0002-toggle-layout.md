# REQ-0002 表示切り替えで下のボタンの位置が動かないようにする

## 0. 読み方（確かめた範囲）
- 「確認」は、2026-10-30 に本リポジトリのコード（extension/content.js、extension/panel.css）と文書を読んだこと。実機での測定（実際のピクセル値、画面サイズごとの差）はしていない。
- 「未確認」と書いたものは事実ではなく、実装前に確かめる点として 8章に並べた。

## 1. 背景と目的
### 1.1 背景
- 初回の試用（PLY-0001）で、ヒートマップから折れ線に切り替えるとタイムラインの高さが変わり、下の「スコア順／時系列順」ボタンが約75px下にずれた。切り替え直後に同じ位置を押すと、別の場所を押してしまった（FB-0001 の FB-3。優先度は低。押し直せば済む程度の困りごと）。
- 1人・1本・1回の試用での観察であり、他の画面サイズでの再現は FB-0001 の時点では未確認だった。

### 1.2 現状の挙動（コードで確認した事実）
| 項目 | 確認した内容 | 根拠 |
|---|---|---|
| 高さが変わる原因 | グラフ（canvas）の高さを、表示に応じて毎回計算して決めている。1行の高さ `rh` が、ヒートマップは 18、折れ線は 38。canvas の高さ H = MARK_H(9) + 行数 × (rh + GAP(3)) + AXIS_H(16)。canvas の下に「スコア順／時系列順」のボタンの列（`.hlx-toolbar`）と候補一覧が続くため、canvas の高さの差がそのままボタンのずれになる | content.js 324・331・332・334行 |
| ずれの大きさ（計算値） | 4行がそろっている場合、ヒートマップ 109px、折れ線 189px。差は 4 × (38 − 18) = **80px**（CSS ピクセル）。PLY の「約75px」は目測と思われ、80px との差の理由は未確認 | 同上（行数 `rows()` は、値の配列がある行だけに絞られる。content.js 300〜311行。通常は4行） |
| 画面幅との関係 | H の式に、canvas の幅 W もパネル幅も入っていない。したがって、切り替えによる高さの差は、パネルの幅（通常400px／広げた760px）やウィンドウ幅では変わらない見込み。ただし `.hlx-hint`（グラフ下の説明文）の折り返し行数は幅で変わる。これは切り替えの前後では同じなので、ずれの差には効かない見込み（実測は未確認） | content.js 332行、panel.css 94・102・112行 |
| 表示範囲・パネル幅の変更 | 表示範囲（全体／前後15分／前半／後半）と ⇔ ボタンは、`drawChart()` を呼び直すだけで、H の式に入らない | content.js 89・92〜95行 |
| 再描画の条件 | `drawChart()` は、パネルが開いていて `data-view` が `done` のときだけ描く | content.js 329行 |
| 既存のテスト | E2E（tests/e2e/test_extension_e2e.py）に、折れ線への切り替えや、切り替え前後の位置を確かめるテストは無い。ビューポートは 1400×1000 のみ | test_extension_e2e.py 173・197・257・319行 |
| パネルの高さ | パネル自体は `height: calc(100vh - 56px)` の固定で、はみ出す部分は縦スクロール（`overflow-y: auto`）。パネルの高さは切り替えで変わらないが、中身の長さが変わる | panel.css 36〜39行 |

### 1.3 目的
- 切り抜き師が、表示を切り替えた直後でも、並べ替えボタンや候補一覧を同じ位置で押せるようにする。切り替えでグラフより下の部分が動かないようにする。
- 切り替え機能そのもの、4行のタイムライン、見どころの▼、再生位置の線、クリックでジャンプは、残す（FB-0001 の G-4）。

### 1.4 範囲外
- FB-1（コメントが少ない配信での候補の信頼度表示・警告）：新機能で、社長判断の対象。本書では扱わない。
- FB-2（候補クリック後の再生位置のずれの疑い）：不具合の可能性の確認で、保守運用課の担当。本書では扱わない。
- FB-4（同じコメ率の行が無色のときの「該当なし」表示）：本書では扱わない（FB-1 とまとめて扱う案が出ている）。
- 候補一覧そのもの、並べ替えの動き、グラフの色・指標の計算・目盛りの変更。
- manifest の権限の追加、新機能の追加、共通指標仕様（shared/）の変更。

## 2. 利用場面（切り抜き師がどう使うか）
1. 切り抜き師が解析を終え、初期表示のヒートマップで山の位置を見る。
2. 「折れ線」に切り替え、山の形を細かく見る。
3. 切り替えた直後に、候補を「時系列順」にしたくて、並べ替えボタンを押す。このとき、ボタンが切り替え前と同じ位置にあれば、狙った場所を押せる。
4. 「ヒートマップ」に戻しても、同じ位置のままである。
5. パネルを広げたり、ウィンドウの大きさが違う環境でも、同じように使える。

### 3.2 実現方法の方針候補（確定は設計課）
どの案でも、グラフ領域の高さを両表示で同じにすることが共通。高さをそろえるには、どちらかの表示の行の高さか、余白が変わる。したがって、見た目が少し変わる。

| 案 | 内容 | 変わる見た目 | 注意 |
|---|---|---|---|
| 案1（推奨） | 両表示の高さを、大きい方（現行の折れ線の189px）にそろえる。ヒートマップは行を太くして埋める | ヒートマップ（初期表示）の各行が約18pxから約38pxに太くなり、パネル全体の中でグラフが約80px 縦に伸びる。候補一覧は、初期表示より約80px 下から始まる | 情報は減らない。ただし初期表示の候補一覧の位置が下がる。見た目は未確認（実装後に画像で確認） |
| 案2 | 両表示の領域を189pxにそろえ、ヒートマップは従来の行の高さのまま、下に余白を足す | ヒートマップの描画は従来どおりだが、グラフの下に約80pxの空白ができる | 空白が不自然に見える可能性がある。初期表示の一覧の位置が約80px 下がる点は案1と同じ |
| 案3 | 両表示の高さを、小さい方（現行のヒートマップの109px）にそろえる。折れ線は行を低くする | 折れ線の各行が約38pxから約18pxに縮み、波の起伏が読み取りにくくなる可能性がある。初期表示の一覧の位置は変わらない | 折れ線の読み取りやすさが下がるおそれ（未確認）。折れ線は「山の形を細かく見る」ための表示 |
| 案4 | 両表示に共通の中間の行の高さを決める（例：約28px） | ヒートマップは太くなり、折れ線は低くなる。どちらも少しずつ変わる | 中間値の決め方は設計課。どちらの表示でも見やすいかは未確認 |

- 「ボタン類をグラフの上に動かす（並べ替えボタンをグラフの前に置く）」案もあるが、画面の構成が大きく変わるため、本書の範囲外とする（別の案件として扱う）。
- どの案でも、グラフを縦に切ったり、グラフの中にスクロールを出したりしない。

## 5. 受け入れ基準
位置の比較は、同じスクロール位置（パネルの `scrollTop` が同じ）で行う。1px の許容は、小数点の丸めのため。

| No | 条件（〜のとき〜になる） | 確かめ方 |
|---|---|---|
| A-01 | 解析が終わった状態で、ヒートマップから折れ線に切り替えるとき、「スコア順」ボタンと「時系列順」ボタンと候補一覧の最初の行（`.hlx-row`）の `getBoundingClientRect().top` の、切り替え前後の差が 1px 以内になる | E2E（模擬YouTube）。切り替え前に各 top を記録し、「折れ線」ボタンを押し、`drawChart` の完了を待って（例：canvas の高さの値が安定するまで）再取得して比較する |
| A-02 | 同様に、折れ線からヒートマップに戻すときも、差が 1px 以内になる | 同上 |
| A-03 | ヒートマップ→折れ線→ヒートマップを5往復しても、毎回の top が最初の値から 1px 以内である（少しずつずれない） | E2E（5往復して毎回記録） |
| A-04 | 両表示の canvas の高さ（`getBoundingClientRect().height`）の差が 1px 以内である | E2E |
| A-05 | パネルを広げた状態（⇔）にして A-01〜A-04 を行うとき、同じく成り立つ | E2E（⇔ を押してから実施。広げた後の再描画を待つ） |
| A-06 | ブラウザのウィンドウ幅を 1400px、800px、500px 程度に変えて A-01〜A-04 を行うとき、同じく成り立つ。表示範囲を「前後15分」「前半」「後半」にしても同様 | E2E（`viewport` を変えて繰り返す。500px 以下では、パネルが `max-width: 100vw` で縮む場合の挙動も確かめる）。表示範囲は select を操作して実施 |
| A-07 | どちらの表示でも、グラフに4行のラベル、見どころの▼（見どころの数ぶん）、再生位置の線、横軸の目盛りが描かれる | E2E：canvas を読み出して該当位置の画素を確認（既存の `GAP_INK_JS` と同じ方法を流用する）。または手動で画像確認（`timeline.png` と同様に保存して目視） |
| A-08 | どちらの表示でも、グラフ中央をクリックするとき、動画の再生位置が「その時刻 − leadSec」付近（既存テストと同じ許容）に移る | E2E（既存の `test_panel_analysis_and_video_sync` と同じ確認を、折れ線でも行う）。動画の再生には ffmpeg が要る（無ければ既存テスト同様に省略） |
| A-09 | 再生位置の線と、シークバーで指した位置の点線が、折れ線でも描かれる | E2E（既存の `near()` の確認を折れ線でも行う） |
| A-10 | 切り替えを行っても、「スコア順」「時系列順」を押すと並びが変わり、一覧の先頭の候補が期待どおりになる | E2E（切り替え後に並べ替えボタンを押して、先頭の行の時刻が変わることを確認） |
| A-11 | 既存の単体テスト・E2E・共通指標仕様の適合が全て通る | `node --test "tests/unit/*.test.js"`、`python -m unittest discover -s tests/e2e -v`、`python shared/reference/metrics_ref.py --check` |
| A-12 | 実際のアーカイブ（実配信）で、切り替えの前後に並べ替えボタンが動かず、YouTube のページの表示が崩れない | 手動（運用係。Claude in Chrome で実配信を開いて確認。画面サイズ別の確認は運用係が可能な範囲で） |
| A-13 | `manifest.json` の permissions・host_permissions・content_scripts に差分が無い | `git diff` |

- E2E で確かめられるか：A-01〜A-10 は、既存の模擬YouTube（解析が `done` になるところまで）の流れで確かめられる見込み。現行のE2Eは位置の比較をしていないため、新しいテストの追加が必要（開発課・品質保証課のテスト係。TS-0002 で定義）。A-07・A-08・A-09 のうち画素の確認は、既存の `GAP_INK_JS` の作りに依存するため、実装時に流用できるかを確かめる（未確認）。
- 現状でA-01 を行うと、差は計算上 80px になり、基準を満たさない（修正前にテストが失敗することの確認にも使える）。

## 6. 影響範囲
- **共通指標仕様（shared/）への影響：なし。** 変えるのは描画の高さ（表示の配置）だけで、コメント量・加速度・同じコメの流れる確率の定義と、スコアの算出は変えない。根拠：高さを決める `rh` と H の計算（content.js 324〜332行）は表示のためだけに使われ、`rows()` の値の計算（analyzer）には入っていない。
- **相手の部（アプリケーション部）への影響：なし。** in App版は別の画面（PCツール）で、本件はパネルの描画の高さの話であり、共通の仕様に触れない。in App版の画面の作りは本調査で読んでおらず、未確認だが、本件は shared/ に触れないため、影響の連絡は不要と判断する。
- **既存機能への影響：** 切り替えとグラフの見た目の高さが変わる（3.2 のとおり、案により、ヒートマップの太さか余白、折れ線の高さが変わる）。それ以外の機能（解析・ジャンプ・並べ替えなど）は変えない。初期表示（ヒートマップ）の候補一覧の位置が下がる案（案1・2）では、解析直後に一覧が見える量が約80px 減る（1画面で見える候補が減る可能性。実画面での影響は未確認）。
- **現状仕様書（spec-current.md）：** 実装後に更新が必要な箇所は、タイムラインの項（切り替えで高さが変わる旨の記述があれば、その削除と、高さの決まり方）。現状仕様係が実装後に反映する。本書の作成では編集していない。
- **担当の見込み（`.claude/hooks/ownership.json` で確認していない。CLAUDE.md 4章の表から）：** `extension/content.js`・`extension/panel.css` は View係。高さの値を共通の定数に切り出す場合の置き場は、設計課が決める。テストは `tests/e2e/**`（品質保証課のテスト係、開発課の各係）。

## 7. 社長判断が必要な点
- **判断待ちIssue：不要と考える。** 根拠：使い方（操作の手順）は変わらず、切り替え機能も残り、権限・新機能・共通指標仕様の変更を含まない。部長の判断記録（board.md）の「使い方・出力は変わらないため社長判断不要」の判断に沿う。
- **部長・課長に確認してほしい論点：** 高さをそろえるには、ヒートマップか折れ線のどちらかの見た目が変わる（3.2 の案1〜4）。案1・2 では、初期表示のヒートマップが約80px 縦に伸びる。案3 では折れ線が低くなる。これを「出力の大きな変更」とみなすかは線引きが微妙なため、念のため挙げる。私は、グラフを切ったりスクロールを出したりせず、情報も増減しないので、軽微な見た目の調整で社長判断は不要と考える（推奨）。ただし「どれが見やすいか」の好みは、社長・プレイヤー代理課の確認が望ましい（実装後に画像で確認）。
- 次の場合は社長判断に上げる：どちらかの表示で、行が縦に切れる、グラフ内にスクロールが出る、行の数や指標が減る、ボタンの置き場所を変える（案としては出るが範囲外）、manifest の権限を足す。
